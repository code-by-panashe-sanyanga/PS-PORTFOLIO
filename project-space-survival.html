Space Survival

Year 1 · 6G4Z0020 Programming · Don't Crash!! coursework

1. Purpose and tech stack

Space Survival is my Year 1 Programming coursework: a 2D avoid the obstacles game in Java Processing. The player stays centred. Arrow keys move every obstacle the opposite way (LEFT shifts obstacles right, UP shifts them down, and so on). Obstacles also carry their own speedX / speedY so the field keeps moving when no key is held. I used an asteroid / space survival theme so the relative motion reads clearly in the first seconds of play, which matters because markers see hundreds of submissions.

2. Design

The control model is inverted from a typical scroller: the ship stays fixed in screen space while the world shifts under key input. That matches the specification and keeps collision math centred on one player position. Obstacles live in an ArrayList (or array), spawn over time, and leave memory when they leave play or are destroyed. Higher bands ask for a second obstacle type, inheritance, player facing art by direction, animation frames, polymorphism in the entity list, and optional file backed high scores. 

draw() loop
  -> read keys: shift all obstacles opposite to arrow
  -> each Obstacle updates speedX/speedY
  -> Player.collision(Obstacle) -> boolean
  -> on hit: lose life / end / effect
  -> ArrayList<Obstacle> may hold subclasses (polymorphism)
  -> optional: score, levels, high score file, explosion frames

3. Features implemented

  • Player fixed at centre; arrow cluster moves the obstacle field
  • At least two classes (Player and Obstacle) with a boolean collision API
  • Multiple obstacles on screen with independent motion
  • PImage based sprites once shapes were stable
  • ArrayList management: spawn new hazards, remove finished ones
  • Additional entity type via inheritance where the band required it
  • Direction dependent player render
  • Development report mapping features to grade bands with code references

6. Challenges and how they were handled

ChallengeApproach
Relative motion feels wrong at first Lock player to centre; apply opposite deltas to every obstacle on key press
Leaking obstacle objects Remove from the list (or null) when off screen or destroyed
Graphics eating the schedule Start with shapes; add PImage only after collision and spawning worked
Proving features to markers Report lists tab or method names for each band; make the first two minutes of play obvious

7. Testing

  • Arrow keys move the field opposite to the press
  • Collision returns true at the expected distance and triggers a visible fail or life loss
  • Obstacles keep drifting with no key held
  • New obstacles appear over time; removed ones do not linger in the list
  • Subclassed obstacles still collide through the shared API (polymorphism check)
  • Sketch runs without errors; broken experiments stay commented out for hand in

8. Deployment and links

Open the sketch in Processing and run. Moodle hand in was a zip named with student name and id, plus the development report. The GitHub copy is portfolio evidence of the OOP game loop and collision design.
