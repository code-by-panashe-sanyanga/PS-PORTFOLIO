What's For Dinner

Year 2 · 6G5Z0023 Thematic Project · group

1. Purpose and tech stack

What's For Dinner is a Year 2 Thematic Project (1CWK100) recipe finder. The brief put us on a product with a real use case: help people cook with ingredients they already have, cut food waste, and browse meals by cuisine. The team chose a responsive website over a store app so we could ship a browser MVP within the unit timeline.

My contribution sat across delivery and code. Roles were not titled formally, but I took on informal lead work: research, page development, supporting teammates who were stuck, and keeping tasks moving on Teams and Trello when progress stalled. The MVP we agreed as a team shipped: ingredient input, recipe suggestions from a matching path, and country or cuisine browse. Saved favourites and full user accounts were scoped out for later so the core path stayed finishable.

Layer Choice Reason
Client HTML, CSS, JavaScript Multi page UI, shared navigation, responsive layout for phone and desktop
Server / data Python backend serving recipe data Keep matching and recipe content off hard coded page markup where possible
Collaboration GitHub, Trello, Microsoft Teams Parallel work, visible task board, daily style check ins
Delivery style Staged Agile (research, design, build, test) Adapt when a feature overran without restarting the whole plan

2. Design

The product path is deliberately short. A visitor lands on home, either searches by ingredient or keyword, takes an inspiration route (dish of the day style prompts), or browses by country. Shared CSS and navigation keep every page one product, not a set of mismatched student pages.

flowchart TD Home[Home] --> Search[Ingredient / keyword search] Home --> Browse[Browse by cuisine] Home --> Inspire[Inspiration / dish of the day] Search --> Match[Recipe matching] Browse --> Match Inspire --> Match Match --> Detail[Recipe view] Detail --> Backend[Python recipe data]

Matching is the architectural centre: user inputs map onto recipe records rather than dumping a static list. That kept the social goal (use what you have) tied to the data model instead of to marketing copy alone. We also treated cuisine content as something to check for accuracy and cultural care, not filler text.

3. Features implemented

  • Ingredient and keyword search that returns workable recipe suggestions
  • Browse by country or cuisine
  • Inspiration path when the user has no fixed dish in mind
  • Responsive layout tested for desktop and phone widths
  • Shared navigation and styling across pages
  • Python backed recipe data for the matching path
  • Team process: Trello board, Teams for blockers, GitHub for parallel commits

Explicitly not in the MVP: saved favourites and production grade accounts. Those were listed as future work so GDPR and password storage did not block shipping the core finder.

6. Challenges and how they were handled

Challenge Approach
Git merge conflicts breaking layout Communicate on Teams before push; Trello ownership so two people were not editing the same file blind
Uneven effort across the group Redistributed tasks; chased updates; carried gaps so the MVP still shipped (lesson: set expectations earlier next time)
Scope vs time Cut favourites and accounts; protect search, browse, and matching
Ethics and legality Accurate cuisine content; Equality Act minded UI (readable type, clear nav, responsive); GDPR noted for any future account data
Security for a later account feature MVP kept personal data minimal; password protection planned for a real account release rather than bolted on late

7. Testing

Testing was manual against the team MVP definition and the unit brief. We did not run a separate automated suite in this module; confidence came from browser checks and demo rehearsal.

  • Ingredient search returns relevant recipes, not empty or random noise
  • Cuisine browse lists the expected dishes
  • Navigation is consistent on every page
  • Layout holds at phone width and desktop width
  • Demo path (home to result) completes without dead links
  • After merge fixes, previously broken CSS no longer regressed the shared shell

8. Deployment and links

The site is static frontend pages plus a Python backend folder in the repo. Open the root index.html (or serve the folder with a local static server) and start the backend if live data is required. Source and write up live on GitHub; demonstration video was submitted via MMUTube for the unit.
