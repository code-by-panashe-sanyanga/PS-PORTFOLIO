Vault Comics

Year 1 · 6G4Z0024 Web Development · individual

1. Purpose and tech stack

Vault Comics is my Year 1 Web Development coursework (1CWK100): a structured site that mimics a payment gateway flow on a small e commerce catalogue. The brief required a home page of products, a pay page that validates Mastercard details in JavaScript, a POST of JSON to the university credit card API, and a success page that shows a masked card ending. I themed the shop as comics rather than generic books so the catalogue felt specific while still meeting every required page and validation rule.

Layer Choice Reason
Markup HTML5 (index.html, pay.html, success.html) Exact three page flow demanded by the specification
Presentation Single CSS file under css/ Brief forbade an MVC layout; one stylesheet keeps styling consistent
Behaviour JavaScript under js/ All card checks and the API call had to be client side JS (no marks for other languages)
Remote check POST JSON to MMU /node/api/creditcard Second validation layer after local regex and field rules

2. Design

The architecture is a linear checkout pipeline. Home lists at least four products with image, short copy, and a Pay control. Pay collects card fields, runs local validation, then posts to the server. Success only appears after a 200 response and shows **** **** **** 1234 style masking for the last four digits.

flowchart LR Home[index.html catalogue] -->|Pay| Pay[pay.html] Pay -->|local JS validation| Local{Pass?} Local -->|no| Pay Local -->|yes POST JSON| API[MMU creditcard API] API -->|200 OK| Success[success.html masked card] API -->|error| Pay

Responsive rules were part of the mark scheme: product list two columns on desktop, one column on phones. Navigation includes Home, About Us, and Contact Us as required (About and Contact did not need full pages). Folder layout follows the brief exactly: root HTML, js/, image/, css/.

Card validation rules implemented in JavaScript

  • Sixteen digits for the Mastercard number
  • Prefix in 51, 52, 53, 54, or 55
  • Expiry not in the past
  • CVV length 3 or 4
  • On failure, keep the user on the form; on success, POST { master_card, exp_year, exp_month, cvv_code } and handle API errors

3. Features implemented

  • Catalogue home with face images, short blurbs, and Pay actions
  • Responsive product grid and navigation behaviour for small screens
  • Pay form with full client side Mastercard checks
  • JSON POST to the assessment API and error handling for bad payloads
  • Success page returning masked last four digits
  • Usability and accessibility checklist in the accompanying report (five points minimum)

6. Challenges and how they were handled

Challenge Approach
All validation marks sit in JavaScript Keep checks in js/; never rely on HTML5 alone for the graded rules
API rejects malformed JSON Build the exact payload shape; branch on non 200 and show a clear retry state
Responsive nav and grid Two column desktop, single column phone; test both before hand in
Directory rules Stick to root HTML + css/js/image; no MVC restructure

7. Testing

  • Reject card numbers that are not 16 digits or wrong prefix
  • Reject expired month or year
  • Reject CVV lengths outside 3 to 4
  • Accept a valid Mastercard shaped number and reach success with masked digits
  • Force a bad POST and confirm the UI reports the error without navigating to success
  • Resize to phone width: catalogue stacks to one column; nav remains usable

8. Deployment and links

Static site: open index.html or serve the folder locally. The pay step needs network access to the MMU credit card endpoint used in the module. Source is on GitHub; the Moodle hand in was a zip of code plus the usability report.
